# Zig typed arrays and DataView

Implement flat-format binary views against devalue **5.9.4**, using Zig **0.17.0**. The user authorizes plan consensus with Claude Opus, implementation after ratification, implementation consensus, and PR/squash merge. The native-client pilot is elsewhere. Correctness comes before tuning; ordinary native tests and recorded upstream bytes are sufficient validation machinery.

## Desired behavior

The graph can express every upstream typed-array kind (including Float16Array) and DataView. A view has its own reference identity and references one graph-owned ArrayBuffer handle, with a byte offset and an element count (typed arrays) or byte length (DataView). Equal distinct views remain distinct; repeated views, shared buffers, and surrounding cycles retain identity. All backing bytes, including bytes outside ordinary subviews, are serialized exactly as upstream does. The codec transports bytes rather than interpreting numeric elements, so NaN payloads, negative zero, large integers, host alignment and endianness do not alter them.

Expose `TypedArrayKind`, a typed-array node, a DataView node, `Graph.typedArray(kind, buffer, byte_offset, length)`, `Graph.dataView(buffer, byte_offset, byte_length)`, and `Graph.viewBytes(value)` returning a borrowed read-only visible byte slice under existing Graph lifetime rules. Constructors require an ArrayBuffer node in the owning graph, validate bounds and typed alignment, and use division/subtraction to avoid arithmetic overflow. Buffer storage is copied only by `arrayBuffer`; creating a view allocates only metadata. `Graph.uint8ArrayCopy(bytes)` copies the visible bytes into a fresh buffer and view, the native equivalent of upstream's Node Buffer normalization. Calling it twice yields distinct buffers; retaining its returned handle preserves repetition. Document on view constructors and in README that subviews serialize their entire backing buffer, and point to uint8ArrayCopy for visible-byte-only output. No numeric conversion helpers or mutable/resizable/shared-memory buffer API are needed for this increment.

Encoding uses the existing flatten/reference cache. A full-buffer view emits `[tag,buffer_reference]`; a shorter view emits `[tag,buffer_reference,byte_offset,length]`, with typed lengths measured in elements. DataView uses bytes. Reducers retain their current precedence, including replacement of a view or its buffer.

Decoding recognizes all thirteen view tags and verifies that the referenced raw wire slot is tagged ArrayBuffer before hydrating it. This matches upstream's guard against circular/array-like allocation attacks. After any ArrayBuffer reviver runs, require an actual ArrayBuffer graph node; reject numbers, objects, arrays, other views and invalid handles without allocating storage from a claimed length. View-tag revivers retain their existing override behavior. Accept omitted bounds (whole buffer), offset alone (remaining buffer), or explicit offset/count. Whole/remainder typed views require a divisible byte extent; explicitly bounded typed views can use an odd-sized backing buffer if their own extent fits. Require finite nonnegative safe-integer bounds and valid tag arity: JS coercion of string/null/fractional bounds (including fractions between -1 and 0) and ignored extra fields remain a documented strict-decode exception; negative integer bounds are rejected by both. JS null length means zero elements, not the remaining extent. Public construction reports InvalidType for invalid buffer/geometry (InvalidHandle for bad handles); malformed wire and revived non-buffer values report InvalidDocument (decode maps constructor InvalidType explicitly); invalid callback handles retain InvalidHandle. Allocator failure remains OutOfMemory.

## Evidence and validation

Authoritative sources are pinned `v5/node_modules/devalue/src/{stringify,parse,operations}.js`, and tag v5.9.4 tests copied under `ephemeral/upstream-5.9.4/`: the binary fixtures and repetitions in `index.test.js`, all flat synchronous behaviors in `buffer.test.js`, and view-backing-buffer cases in `parse-operations.test.js`. Source links: https://github.com/sveltejs/devalue/tree/v5.9.4/test and https://github.com/sveltejs/devalue/tree/v5.9.4/src .

Extend the existing pnpm/JS recorder with manually authored binary inputs and a dedicated fixture file, using only pinned upstream to produce expected wire bytes. Require Float16Array at recording time and assert binary fixture count in native tests. Native Zig tests build their encoder inputs independently and compare decoded kind, bytes, offset/count, and handle topology independently. Cover every kind across full/sub/empty views, shared buffers, repeated and distinct views, cycles, raw float/integer bit patterns, the distinct invariants of all upstream Node Buffer sources (visible bytes, empty copy, distinct backing copies, repetition/cycles), and the ordinary-browser equivalent without Node globals. Record every JS source as evidence, but collapse equivalent native invariants rather than duplicate native tests for host allocation methods/file I/O. JS pooling, filesystem ingestion, realms, subclasses, getters/proxies, unflatten/operations overrides, expression generation and promise scheduling have no corresponding native API; port their observable flat wire/identity/buffer-validation invariants and identify the invocation mechanics rather than claiming those APIs exist.

Port all view-specific upstream invalid cases, and the per-kind revived-buffer matrix for genuine buffers, empty buffers, invalid lengths/array-like/object/view results, cached previously revived buffers and custom cycles. Add overflow/alignment/range/arity/type guards, input lifetime, graph growth, allocation-failure enumeration through copying/construction/encode/decode/revivers, and include binary fixtures in existing deterministic corpus mutation tests. Use leak-checking allocation and the existing deterministic failure-injection allocator.

Both Go modules currently implement typed arrays/DataView only for expression generation, not flat Stringify/Parse; Float16Array is absent entirely. Compare standalone backing-buffer bytes and the existing shared corpus with both modules, and record their current rejection of flat view tags explicitly. Binary-view parity is validated against pinned JS and independent native contents/topology, not claimed against an absent Go flat implementation. Do not expand Go scope silently. Run a fresh path-dependency Zig consumer with shared views and offsets. Run `just test`, `just lint`, and Zig ReleaseSafe tests. Update README and the hand-written upstream coverage note to distinguish completed flat binary behaviors from the remaining feature/API differences. Existing Go APIs, shared golden cases, and unrelated Zig features remain unchanged. Opus reviews the full plan first, then the entire implementation/proof; resolve material findings before creating and merging the PR with green CI.
